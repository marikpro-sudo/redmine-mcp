# Создание задач SAP с выбором статуса — версия 0.4.0

Доступны все пять типов: «Ошибка», «Доработка», «Новая разработка», «Консультация», «Перенос SAP».
Разработчики и руководители могут создавать задачи в любом статусе, используемом в процессе выбранного
типа. Речь о начальном статусе; переходы уже существующих задач и обязательные поля не меняются.
Новая версия требует серверный модуль redmine_completed_work 1.1.0 (schema_version=2).

## Обязательный вопрос о статусе

Перед **каждым** созданием ИИ читает доступные статусы и спрашивает пользователя:
«С каким статусом создать задачу?». Не выбирает статус автоматически.
Если исходная команда уже содержит статус, кратко уточняет его и ждёт ответа:
«Создаём в статусе „Тестирование“?». Подтверждение относится только к этой задаче.

Лишь после ответа можно подготовить операцию с обязательными status и status_confirmed=true.
Этот флаг фиксирует обязанность харнесса дождаться ответа; сам сервис не может удостоверить человеческий ответ.
После выбора статуса и получения необходимых сведений отдельное подтверждение публикации не требуется.
Правило подтверждения вопросов бизнес-заказчику из COMMUNICATION.md остаётся отдельным правилом.

## Сбор сведений

1. Вызвать redmine_creation_context без status: получить типы и доступные начальные статусы.
2. Уточнить тип при неоднозначности, задать вопрос о статусе и дождаться ответа.
3. Повторить redmine_creation_context с выбранным status: получить поля, обязательность и возможные значения
   именно для выбранного статуса. Сведения другого статуса использовать нельзя.
4. Установить модуль SAP и бизнес-заказчика для типов, где есть это поле. Если уже указаны явно — не спрашивать
   повторно. Заказчика сопоставить с реально предлагаемым ID; при совпадении имён уточнить.
5. Одним сообщением запросить недостающие обязательные данные и ждать ответа.
   Для «Новой» разработки не требовать отчёта о ещё не выполненных тестах и транспортах.
   Для «Переноса SAP» запросить его обязательные поля: исходную заявку, целевую систему, порядок импортов,
   зависимости, инструкцию, действия при неуспехе, подтверждение тестирования и, при необходимости,
   окно переноса и результат. Точный набор определяет текущий workflow.
6. Составить тему и описание. Для выполненной работы — цель, фактические изменения и проверки;
   для новой — запрос и ожидаемый результат. Не выдумывать выполнение, приёмку, транспорты или даты.
7. Выполнить prepare, затем apply; вернуть номер, ссылку, фактический статус и результат проверки.

## Поля и значения по умолчанию

Обязательные аргументы prepare: tracker, status (точное имя либо ID), status_confirmed=true,
subject, description, sap_module. project берётся из аргумента или REDMINE_PROJECT.
Исполнитель — текущий подключённый пользователь, включая руководителя.

business_customer, acceptance_criteria, dev_transports, test_system, test_result задаются, когда применимы
и требуются выбранным процессом. business_customer может быть точным однозначным именем или ID.
ai_participation по умолчанию «ИИ помогал», если поле есть у типа; проверку разработчиком не утверждать без факта.

Дополнительные поля передаются через custom_fields: массив объектов с id и value. ID берётся из контекста.
Поддерживаются string/text/int/list/user, а для множественного поля — массив строк. Для int значение — строка
с целым числом. Для user и list допускаются только значения из options. Нельзя передавать одно поле дважды
через именованный аргумент и custom_fields, скрытые/недоступные поля или значения вне справочника.

Закрытый статус (включая «Закрыта», «Выполнена», «Отклонена») — 100%. Открытый — 0% либо явно заданный
done_ratio от 0 до 100. При серверном расчёте готовности по статусу используется заданное сервером значение;
конфликт с явным процентом приводит к отказу. Приоритет остаётся серверным, часы и даты не придумываются.

## Инструменты

| MCP/HTTP | CLI |
|---|---|
| redmine_creation_context | creation-context |
| redmine_prepare_create_issue | prepare-create |
| redmine_apply_create_issue | apply-create |
| redmine_get_operation | operation |

Пример безопасного чтения:

    node --env-file=.env src/cli.js creation-context
    node --env-file=.env src/cli.js creation-context '{"status":"Новая"}'

Учебный examples/completed-work.json содержит status_confirmed=false намеренно: его нельзя отправить
без ответа пользователя и замены заглушек реальными данными.

## Надёжность и обновление

Черновик живёт 30 минут; перед POST повторно проверяются текущая учётная запись, начальный статус и поля.
Статус сохраняется по точному ID, переименование не перенаправляет запись на другой статус.
После создания проверяются все отправленные поля, процент и признак закрытия.
Один operation_id допускает одну попытку POST, включая повтор, параллельные вызовы и перезапуск.
При uncertainty не создавать новый черновик автоматически: сначала установить результат в Redmine.
Защита локальна, не объединяет разные компьютеры и независимые ID. Обычные уведомления Redmine возможны.

Старый модуль schema_version=1 приводит к SERVER_UPGRADE_REQUIRED, без записи.
Неисполненные черновики версии 0.3 без выбора статуса отклоняются: сначала нужно спросить статус.
Уже применённые операции возвращают сохранённый результат без повторной отправки.
Обновление сервера выполняется отдельным upgrade-creation-statuses.sh; старый установщик повторно не запускать.
После установки обновления перезапустить MCP-процесс.
