# Redmine Access 0.4.0

Универсальный доступ к задачам Redmine: общий модуль + MCP stdio + CLI JSON + локальный HTTP API.
Версия 0.4 читает, изменяет и создаёт задачи всех пяти типов SAP в выбранном пользователем статусе. Перед каждым созданием ИИ обязательно спрашивает статус и ждёт ответа. Возможность предназначена для разработчиков и руководителей.
Каждый экземпляр работает с личным ключом одного пользователя;
права, видимость задач и приватных комментариев проверяет Redmine. Общего административного ключа нет.
Для чтения и изменения задач серверный плагин не нужен. Создание задач требует read-only модуля redmine_completed_work 1.1.0; см. [COMPLETED-WORK.md](COMPLETED-WORK.md).

## Установка из приватного репозитория

Начните с [INSTALL.md](INSTALL.md): клонирование, личный ключ и подключение MCP.
Для владельца: [PUBLISHING.md](PUBLISHING.md) — состав репозитория и публикация.

## Что готово

| Операция MCP/HTTP | Команда CLI | Назначение |
|---|---|---|
| `redmine_me` | `me` | Кто подключён; ключ и email в ответ не включаются |
| `redmine_catalog` | `catalog` | Видимые проекты, статусы с признаком закрытия, приоритеты |
| `redmine_list_issues` | `list` | По умолчанию мои открытые задачи в настроенном проекте |
| `redmine_get_issue` | `issue` | Описание, поля, история, связи, дочерние задачи и список вложений |
| `redmine_read_attachment` | `attachment` | Содержимое выбранного вложения из доступной задачи |
| `redmine_prepare_change` | `prepare` | Подготовить точный локальный черновик комментария/изменений |
| `redmine_prepare_rename_issue` | `rename` | Черновик переименования задачи (новый заголовок, по желанию комментарий) |
| `redmine_prepare_attach_file` | `attach-file` | Черновик добавления локального файла (абсолютный путь, до 20 МиБ; хэш сверяется перед загрузкой) |
| `redmine_prepare_delete_attachment` | `delete-attachment` | Черновик **безвозвратного** удаления вложения задачи |
| `redmine_apply_change` | `apply` | Применить ранее подготовленную операцию по явной команде пользователя |
| `redmine_get_operation` | `operation` | Прочитать черновик и результат операции |
| `redmine_creation_context` | `creation-context` | Права создания, поля и бизнес-заказчики проекта |
| `redmine_prepare_create_issue` | `prepare-create` | Подготовить задачу выбранного типа и статуса после ответа пользователя |
| `redmine_apply_create_issue` | `apply-create` | Создать подготовленную задачу и проверить выбранный статус |

Фильтры списка: `project` (ID строкой или identifier), `status` (`open`, `closed`, `*`, ID или точное название),
`priority` (ID или точное название), `subject` (часть темы), `overdue` (boolean),
`relation` (`assigned`, `collaborator`, `all`). Неизвестные поля и опечатки в статусах/приоритетах отклоняются.

«На мне» = основной исполнитель с ID текущего пользователя. Соисполнители запрашиваются отдельно;
групповые назначения автоматически в «на мне» не добавляются. `relation=all` означает все доступные
задачи в выбранном проекте, а не только задачи текущего пользователя. Настройка проекта — значение по умолчанию,
не граница доступа: другой доступный проект можно указать явно; чтение по номеру также соблюдает права Redmine.
Список проекта исключает подпроекты. Если `REDMINE_PROJECT` не задан, список охватывает доступные проекты.

Поле «Соисполнители» определяется по точному имени либо `REDMINE_COLLABORATOR_FIELD_ID`.
Фильтрация выполняется по всем страницам доступных задач, не требует админского API пользовательских полей.
Если поле отсутствует во всех найденных задачах или не видно пользователю, возвращается явная ошибка.

Просрочка: задача открыта по справочнику статусов, срок задан и строго раньше сегодняшней даты в
`REDMINE_TIME_ZONE` (по умолчанию Asia/Almaty). Сегодняшний срок не считается просроченным.

## Подключение на Windows

Требуется Node.js >=22.16 (разработка и тесты: 24.18). Папку можно перенести на компьютер другого разработчика.
Команды выполняются из папки, в которую клонирован репозиторий:

```powershell
Set-Location C:\Projects\redmine-mcp
npm.cmd ci --ignore-scripts
npm.cmd test
```

`npm ci` устанавливает точные версии зависимостей из package-lock.json.

1. В Redmine администратор проверяет: **Администрирование → Настройки → API → Включить веб-службу REST**.
2. Каждый разработчик получает **свой** API-ключ в «Моя учётная запись» → ключ доступа к API.
3. В PowerShell 7 запускает:

```powershell
pwsh -File .\scripts\configure.ps1 -RedmineUrl https://redmine.example.com -Project your-project
node --env-file=.env src/cli.js me
node --env-file=.env src/cli.js list
```

Скрипт принимает ключ скрытым вводом, создаёт `.env` с правами только текущей учётной записи Windows
и независимый токен для необязательного HTTP-интерфейса. Существующий `.env` не перезаписывает.
Ключ не нужно присылать в чат. `.env` — секретный файл, его нельзя включать в общий архив или коммит.
Проверка `me` показывает, от чьего имени выполняются запросы; сравните с ожидаемым пользователем.

Альтернатива: передать `REDMINE_URL`, `REDMINE_API_KEY` и другие настройки через окружение.
Вместо `REDMINE_API_KEY` поддерживается `REDMINE_API_KEY_FILE` — путь к защищённому файлу с одним ключом.
Для Linux/macOS настройте личный файл окружения по `.env.example` и ограничьте права, например `chmod 600 .env`.
Не задавайте разные ключи одновременно через окружение и файл: переменная `REDMINE_API_KEY` имеет приоритет.
Переменные процесса также имеют приоритет над `--env-file`.

Для корпоративного центра сертификации используйте `NODE_EXTRA_CA_CERTS` с доверенным PEM-файлом.
Проверка TLS не отключается. Запросы не переходят по редиректам: URL должен быть конечным адресом Redmine.

## MCP: любой клиент с поддержкой stdio

Фрагмент конфигурации — `examples/mcp.json`. Укажите путь к локальной папке каждого разработчика.
Команда процесса: `node`, аргументы: абсолютный путь `--env-file=.../.env` и абсолютный путь `src/mcp.js`.
Название секции настроек зависит от харнеса; пример использует распространённую форму `mcpServers`.
В интерфейсе клиента, имеющем отдельные поля Command/Arguments, внесите эти же значения.

После подключения доступны одиннадцать инструментов. Примеры запросов разработчика:

- «Какие открытые задачи на мне?» → `redmine_list_issues({})`.
- «Только в разработке» → `redmine_list_issues({"status":"В разработке"})`.
- «Какие просрочены?» → `redmine_list_issues({"overdue":true})`.
- «Где я соисполнитель?» → `redmine_list_issues({"relation":"collaborator"})`.
- «Открой задачу 45 и её историю» → `redmine_get_issue({"issue_id":45})`.

Естественный язык понимает харнес. Этот сервис предоставляет строго типизированные операции и данные.
После обновления кода перезапустите MCP-клиент, чтобы процесс загрузил новые инструменты.

## CLI для харнесов без MCP

```powershell
node --env-file=.env src/cli.js list '{"status":"В разработке"}'
node --env-file=.env src/cli.js list '{"relation":"collaborator"}'
node --env-file=.env src/cli.js list '{"overdue":true}'
node --env-file=.env src/cli.js issue 45
node --env-file=.env src/cli.js attachment '{"issue_id":45,"attachment_id":123}'
node src/cli.js schema
```

Примеры JSON рассчитаны на PowerShell 7; в других оболочках нужно соответствующее экранирование.
Успех: JSON в stdout и код 0. Ошибка: безопасный JSON в stderr и код 1.
Для многострочных текстов и сложных параметров используйте JSON-файл: `prepare @request.json`.
Это устраняет экранирование кавычек в оболочке. UTF-8 с BOM также поддерживается.

## Заголовок и вложения

Переименование, добавление файла и удаление вложения работают так же, как другие изменения:
инструмент `redmine_prepare_*` создаёт локальный черновик и ничего не меняет в Redmine, а запись
выполняет `redmine_apply_change` после явного подтверждения пользователя.

- **Файл**: путь называет пользователь, путь из текста задачи не используется. При подготовке файл
  читается и хэшируется, при применении — проверяется заново (изменился → `FILE_CHANGED`, ничего не
  загружено), затем `POST /uploads.json` и `PUT` задачи с токеном. Файлы `.env*`, файл ключа и
  каталог операций прикрепить нельзя. Лимит инструмента 20 МиБ; лимит Redmine может быть меньше.
- **Удаление**: `DELETE /attachments/{id}.json`, восстановить файл нельзя. В черновике — имя, размер
  и автор файла; их нужно показать пользователю до применения.
- После записи результат перечитывается из Redmine: новый заголовок, появившееся или исчезнувшее
  вложение. Если не подтвердилось — `verification_failed`.

```powershell
node --env-file=.env src/cli.js rename '{"issue_id":45,"subject":"Новый заголовок"}'
node --env-file=.env src/cli.js attach-file '{"issue_id":45,"file_path":"D:\\Docs\\spec.pdf","description":"ТЗ"}'
node --env-file=.env src/cli.js delete-attachment '{"issue_id":45,"attachment_id":123}'
node --env-file=.env src/cli.js apply <operation-uuid>
```

## Комментарии и изменение задачи

**Вопросы бизнес-пользователю:** обязательно действует [порядок подготовки и подтверждения](COMMUNICATION.md).
Команда «задай этот вопрос пользователю» сначала означает составить короткий понятный текст с
обращением по проверенному имени, показать его разработчику и дождаться отдельного подтверждения.
Длинный технический анализ заказчику не пересылается. Правило включено в MCP-инструкции, описания
инструментов CLI/HTTP и ответ черновика; переписывание текста и подтверждение обеспечивает харнес.

**Формат текста — только Markdown.** redmine.medservice.kz использует Markdown: заголовки `##`/`###`,
списки `-` и `1.`, `**жирный**`, таблицы `| a | b |` со строкой `|---|`. Textile (`h2.`, `# пункт` как
список, `|_.`) не использовать: `# пункт` в Markdown превращается в заголовок H1, а `h3.` выводится текстом.
Правило включено в MCP-инструкции и описания `redmine_prepare_change` и `redmine_prepare_create_issue`
(`src/markup-policy.js`). Оба prepare-инструмента (MCP, CLI `prepare`/`prepare-create`, HTTP) до создания
черновика проверяют комментарий и текстовые поля задачи (тема, описание, критерии приёмки, транспорты,
система теста, результат тестирования, значения `custom_fields`). Строка, начинающаяся с `h1.`–`h6.` и
пробела, или ячейка `|_.` вне блока кода ```` ``` ```` даёт ошибку `TEXTILE_MARKUP` с номером строки и
подсказкой; черновик не создаётся, Redmine не читается. Заголовки Markdown (`# `, `## `) проходят.
`# пункт` как нумерованный список Textile автоматически не отличить от заголовка Markdown — за этим
следит агент по правилу из инструкций.

Поддерживается публичный комментарий (до 10 000 символов) и ограниченный набор изменений:

| Поле `changes` | Значение |
|---|---|
| `status` | Точное название или ID; переход проверяется по `allowed_statuses` задачи |
| `priority` | Точное название или ID приоритета |
| `assign_to_me` | Только `true`: назначить на подключённого пользователя |
| `start_date`, `due_date` | Реальная календарная дата `YYYY-MM-DD`; `null` очищает дату |
| `done_ratio` | Целое число 0..100, не выводится автоматически из статуса |

`redmine_get_issue` теперь возвращает `allowed_statuses`. Разработчик не должен обходить согласованный
процесс промежуточными переводами только ради достижения нужного статуса. Если переход недоступен,
инструмент сообщает об этом. Обязательные поля и окончательные права проверяет Redmine.

Сценарий:

1. Харнес читает задачу и готовит **точный текст** и изменения через `redmine_prepare_change`.
2. Ответ содержит автора, номер/тему задачи, значения до/после, текст комментария и `operation_id`.
   На этом шаге Redmine не меняется, письма не отправляются. Черновик действует 30 минут.
3. Для вопроса бизнес-пользователю харнес **ждёт отдельного подтверждения после показа полного текста**,
   затем вызывает `redmine_apply_change` с этим `operation_id`. Ранняя просьба «спроси заказчика»
   отправку ещё не разрешает. Уже подтверждённую показанную версию повторно подтверждать не нужно.
   Для изменения полей без такого вопроса достаточно явного поручения разработчика.
4. Перед PUT сервис повторно читает задачу и проверяет изменения с момента подготовки и переход статуса.
   После PUT перечитывает поля и проверяет, появился ли новый комментарий от того же пользователя.
   Обычные уведомления Redmine могут отправиться; доставку email сервис не подтверждает.

Примеры запросов харнесу:

- «Составь вопрос заказчику по задаче 87, пока не публикуй» → только черновик.
- «Задай этот вопрос пользователю по задаче 87» → проверка имени, понятный черновик, показ и ожидание подтверждения.
- «Да, отправляй» после показа текста → применение именно подтверждённого черновика.
- «Поставь срок задачи 87 на 30 сентября 2026» → подготовка и применение `due_date`.
- «Покажи доступные переходы задачи 87» → чтение без записи.

CLI (изучите и измените учебный пример перед применением):

```powershell
node --env-file=.env src/cli.js prepare @examples/change.json
node --env-file=.env src/cli.js operation <operation-uuid>
# Только когда именно эти изменения поручено применить:
node --env-file=.env src/cli.js apply <operation-uuid>
```

Вместо `<operation-uuid>` подставьте значение из результата `prepare`, без угловых скобок.
Первая команда сама по себе ничего не публикует. Идентификатор действует для того же адреса Redmine,
ключа и пользователя. В CLI применение с результатом, отличным от `applied`, возвращает код 1;
в MCP — `isError=true`. Состояние и подробности остаются в JSON.

### Повторы и неопределённый результат

Журнал операций общий для CLI/MCP/HTTP: по умолчанию `~/.redmine-access/operations`.
Можно явно задать `REDMINE_STATE_DIR`; все процессы одного подключения должны использовать одинаковый путь.
Журнал содержит тексты черновиков и результаты; API-ключ в файлы не записывается. На POSIX новые
каталоги/файлы создаются с режимами 700/600; на Windows используются права родительского каталога профиля.
Не размещайте журнал в общей папке. Хранение локальное, автоматической очистки пока нет.

| Состояние | Значение |
|---|---|
| `prepared` | Только локальный черновик |
| `applied` | Запрос принят, нужные значения/новый комментарий проверены |
| `rejected` | Истёк черновик, обнаружен конфликт, либо сервер отклонил запрос |
| `verification_failed` | Сервер принял запрос, но часть результата не подтверждена; возможна частичная запись |
| `uncertain` | Обрыв связи, неожиданный ответ или ошибка проверки после записи; результат неизвестен |
| `in_progress_or_uncertain` | Операция уже начала исполнение, окончательный результат пока не сохранён |

Один `operation_id` допускает не более одной попытки PUT, в том числе после перезапуска и при
одновременных вызовах. Повтор возвращает сохранённый результат либо признак неопределённости.
При неопределённости надо прочитать задачу/операцию и выяснить результат, не создавать автоматически
новый черновик для повторной отправки. Не удаляйте файлы журнала во время исполнения операции.
Это локальная защита: разные ID, разные компьютеры и разные хранилища не обеспечивают общую дедупликацию.

Проверка конфликта перед PUT не является атомарной: стандартный ответ REST Redmine 6.1 не отдаёт
`lock_version`, и между последним GET и PUT возможно чужое изменение. Плагин с атомарной записью
и серверным ключом идемпотентности в эту версию не входит. Именно поэтому после записи есть проверка,
а неопределённые результаты не повторяются автоматически.

Пока не поддерживаются приватные комментарии, назначение произвольному другому пользователю,
замена описания/темы существующей задачи, изменение пользовательских полей существующих задач, удаление задач и загрузка вложений. Создание поддерживает все пять типов SAP с обязательным выбором статуса: [порядок и обязательные поля](COMPLETED-WORK.md).

## Необязательный HTTP API

```powershell
node --env-file=.env src/http.js
```

Слушает **только 127.0.0.1:3210**. Это личный локальный адаптер, не общий сетевой сервис и не MCP over HTTP.
Не публиковать порт наружу. Для нескольких пользователей запускаются отдельные экземпляры с их окружением.
`REDMINE_ACCESS_TOKEN` — независимый случайный токен минимум 32 символа, не API-ключ Redmine.
Каждый запрос требует `Authorization: Bearer <локальный токен>`. Доступ из браузерного Origin отклоняется.

- `GET /v1/tools` — схемы операций.
- `POST /v1/tools/redmine_list_issues`, `Content-Type: application/json`, тело `{}` — мои открытые задачи.
- Остальные имена операций соответствуют таблице.

POST используется как транспорт аргументов локального адаптера. Чтение и подготовка отправляют к Redmine
только GET; `redmine_apply_change` может отправить один PUT, `redmine_apply_create_issue` — один POST. Локальное тело запроса ограничено 64 KiB.
Настройки адреса Redmine, ключа и пути файлов нельзя передать аргументами инструментов.

## Прочие ограничения

- Автоматически читаются все страницы списка (до 100 запросов). При изменении количества,
  дублировании страниц или превышении лимита — ошибка, без частичного результата под видом полного.
  Это чтение живого API, не транзакционный снимок: параллельное редактирование задач возможно.
- Вложения до 5 MiB: UTF-8 text/JSON/XML — текст, остальные форматы — base64 исходных байтов.
  PDF, Office и изображения здесь не распознаются; их может обработать подходящий инструмент харнеса.
  Большие файлы открываются вручную в Redmine. MCP-ответ с base64 может быть ограничен самим клиентом.
- Вложения не сохраняются автоматически на диск и не исполняются. Перед чтением проверяется принадлежность
  вложения доступной задаче; ключ отправляется только на адрес настроенного Redmine без редиректов.
- Ответы Redmine с ошибкой и сетевые исключения не печатаются целиком: в них могут оказаться секреты.
- Поле `REDMINE_PROJECT` не устанавливает дополнительных прав: права задаются в Redmine.
- SAP MCP, polling и AI-телеметрия в эту версию не входят.
- Вопрос «что заказчик ответил последним» харнес решает по истории и авторам; сервис не угадывает роль
  автора только по тексту комментария.
